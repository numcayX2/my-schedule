## Findings

### HIGH

**[1] P4 / R-02 — em dash in shipped text.**
`components/Schedule.tsx:165`: `MON—FRI / 09:00—19:00`. Two em dashes in the only string a user reads on the board heading. Hard Gate, no purpose.
*Fix:* `MON-FRI / 09:00-19:00`.

**Status: FIXED.** `Schedule.tsx` now reads `MON-FRI / 09:00-19:00`. Verified in the rendered page text.

**[2] P4 / R-25 — two text colors fail WCAG AA.**
Measured with the contrast checker:
- `.schedule-day span` `Schedule.css:452` — `#73756e` on `#121310` = **3.99:1** at 8px/800. Needs 4.5.
- `.schedule-footer` `Schedule.css:679` — `#777970` on `#121310` = **4.22:1** at 8px. Needs 4.5.

The day label is the row header of the whole grid; the footer is the only text at the page end. Both are the "just darken it a bit" default.
*Fix (values verified):* `#8e9089` = 5.77:1, `#9b9d94` = 6.79:1. Also delete `--muted` (`Schedule.css:13`), declared and never used.

**Status: FIXED.** The day label is now `#8e9089` (5.77:1) and the footer `#9b9d94` (6.79:1), both confirmed as the computed colors in a production build. The unused `--muted` token is deleted.

**[3] P0 / R-26 — the pointer is hidden with no replacement, and the replacement is optional.**
`Schedule.css:698` applies `cursor: none !important` to `.schedule-root, .schedule-root *` from CSS alone. The dot and ring that replace it are painted by a GSAP effect (`Schedule.tsx:66-108`). If that effect does not run, the entire page has **no visible cursor** while still hiding the OS one. I hit exactly that state: on the `next dev` server the page never hydrates, so the effect never registers, and every computed `cursor` is `none` with a `cursor-dot` stuck at `opacity: 0`.
*Fix:* gate the rule on a class the script adds, e.g. `html.custom-cursor .schedule-root, html.custom-cursor .schedule-root * { cursor: none }`, added from inside the same effect that creates the dot. CSS must never be able to hide the pointer on its own. Drop `.schedule-root *` from the selector so the scrollable grid keeps its own affordance.

**Status: FIXED.** `Schedule.css` now gates the rule on `html.custom-cursor`, a class added by the same effect that creates the dot and removed on its cleanup. Verified against a production build: with the effect running, `documentElement.classList.contains("custom-cursor")` is true and `cursor` still computes to `none`, so the design is unchanged; with the effect not running, the class is absent and the native cursor stays. One deliberate deviation: `.schedule-root *` and `!important` were kept, because the UA stylesheet's own `cursor: default` on `button` beats an inherited value, so scoping to `.schedule-root` alone would leave a second OS arrow sitting on every day button.

**[4] P1 / G-1 — class cards advertise an interaction that does not exist.**
Three separate signals say "clickable": `.class-card:hover` lifts, rotates and saturates (`Schedule.css:505-508`), the custom cursor ring grows to 54px and turns orange over `.class-card` (`Schedule.tsx:82`), and the card carries a 2px ink border plus a hard shadow like a button. Verified in the DOM: the card is `<article>`, `role: null`, `tabindex: null`, and clicking it changes nothing.
*Fix:* pick one. If the card has no detail view, delete the hover transform and remove `.class-card` from the ring's hover targets. If it should open one, make it a `<button>`/`<a>` with a real destination and a focus ring.

**Status: FIXED, first option.** The `.class-card:hover` block, the now-dead `transition` on the card and its dead `prefers-reduced-motion` override are all deleted, and the cursor ring's hover target is now `button` only. Verified: the stylesheet has zero `:hover` rules matching `.class-card`, and hovering a card leaves `transform: none`, `filter: none` and the ring without its `hovering` state.

**[5] P1 / C-3 — on a phone the product does not exist.**
`Schedule.css:751` sets `.schedule-main { display: none }` below 768px, and the mobile view is a flat list of five day stacks. The actual job of a schedule (see the shape of the week, spot a free slot, spot a clash) exists only on desktop. A student on a phone cannot answer "is Wednesday free?" without scrolling 2400px.
*Fix:* a compressed week strip above the list: 5 rows x 10 hour columns, one filled cell per session, tap a cell to jump to that day. It reuses the color coding that already exists and costs about 60px.

**[6] P2 / C-3 — the mobile first screen is 43-49% chrome.**
Measured: at 390x844 the first class card starts at y=410, so **48.5%** of the viewport is dossier header before any schedule data. At 360x800 the header alone is 345px of 800. The least useful pixels on that screen are the stat strip (`12 / CLASS SESSIONS / COURSES 06 / SEMESTER 1-69`), which answers nothing a student asks on opening the app.
*Fix:* on mobile, drop the stat strip to a single line, or move it below the first day section. The title block earns its height; the dashboard does not.

### MEDIUM

**[7] P2 / R-29 — the palette spends its meaning.**
Six saturated hues encode courses (`schedule-data.ts:42-49`), which is a real function. But `acid` and `orange` are also the hazard rail, the header bar, the title accent, the slash, the day count, the legend and the active nav. The color that means "this is NLP" is the same color as the caution tape, so color stops carrying information.
*Fix:* keep the six course hues strictly on data. Chrome returns to paper/ink + one accent, with orange reserved for the hazard motif (rail, stamps, diagonal).

**[8] P2 / R-17 — a literal count next to computed counts.**
`Schedule.tsx:194` hardcodes `SESSION MAP / 12 BLOCKS` while the header computes `CLASSES.length`. Add a class and the legend lies.
*Fix:* render `CLASSES.length`, or drop the count.

**[9] P2 / R-03 — the desktop grid overflows with no cue.**
Measured at 1024x820: `.schedule-main` clientWidth 977 vs scrollWidth 1160, so 183px of the day is off screen. The sticky day column helps, but nothing tells a sighted user the board scrolls horizontally; the instruction exists only in the `aria-label`.
*Fix:* a 24px edge fade on the right of `.schedule-main` that disappears at scroll end. One line of CSS, no new chrome.

**[10] P2 / J-5 — `aria-label` on the card deletes the room number.**
`Schedule.tsx:16` puts an `aria-label` on a non-interactive `<article>`, so the accessible name replaces the content. The name carries day, course and time but drops `ห้อง 105`, `กลุ่ม 2` and LEC/LAB.
*Fix:* drop the `aria-label`. The inner `<time>` elements and the `<abbr title>` already read correctly in order.

**Status: FIXED.** The `aria-label` is gone from the card. Verified: `getAttribute("aria-label")` is `null` and the card's own text now reads `10301351 | 10:00-12:00 | วิทยาการข้อมูล | ห้อง 105 | กลุ่ม 2 | บรรยาย · LEC`, so the room and section are exposed again.

**[11] P2 / R-19 — the load choreography puts the payload last.**
`Schedule.tsx:57-58`: mobile day sections start at 0.5s and cards at 0.58s, behind four hero beats. On a phone the data the user came for waits behind an animation of the parts they scrolled past, and below-the-fold cards animate unseen.
*Fix:* on mobile run one short beat (rail + title), then show day sections immediately. Keep the full timeline for desktop.

**[12] P3 / R-03 — `overflow-x: hidden` on body masks overflow.**
`Schedule.css:24`. There is no overflow to mask today (measured 360/390/1440 all clean), so this only buys the appearance of correctness, and it turns `body` into a scroll container, which is where `position: sticky` silently dies.
*Fix:* delete it. If a breakpoint starts overflowing later, fix that breakpoint.

**[17] P4 / R-35 — RETRACTED. My test environment, not a defect in this repo.**
The symptom was real and reproducible: on two fresh tabs against `npm run dev`, the SSR HTML rendered, the React runtime loaded, but no React root attached, so the day buttons did nothing and GSAP never ran. The same code under `next build` + `next start` hydrated, animated and navigated correctly (trusted click on พฤ. -> scrollY 1388, heading at y=24, active button 4).
Root cause, found after the fact: the automation browser fails the dev server's HMR WebSocket upgrade with `net::ERR_INVALID_HTTP_RESPONSE` on `/_next/webpack-hmr`. A dev page that cannot open its HMR socket never hydrates, which is exactly the symptom I measured. The dev server is healthy: a direct WebSocket upgrade from Node returns `101 Switching Protocols`, and clearing the 326 MB `.next` cache changes nothing.
Do not change anything in this repo for this finding. It matters only as the reason [3] was reachable, and [3] is now closed.
